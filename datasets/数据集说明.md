# 50 题数据集怎样工作

## 一句话说明

每道题向大模型公开“任务要求 + 固定输入/输出接口”；大模型生成一个完整
ST 程序；Oracle 用输入序列、预期输出和形式性质判定程序是否正确。

## 一道最简单的题

题目 `C01_E01_two_input_permissive` 公开以下内容：

- 输入 `Enable : BOOL`；
- 输入 `GuardClosed : BOOL`；
- 输出 `RunPermit : BOOL`；
- 要求：当且仅当两个输入都为 `TRUE` 时，输出为 `TRUE`。

大模型应生成类似下面的候选程序，但数据集不会把答案提供给模型：

```iecst
FUNCTION_BLOCK C01_E01_two_input_permissive
VAR_INPUT
    Enable : BOOL;
    GuardClosed : BOOL;
END_VAR
VAR_OUTPUT
    RunPermit : BOOL;
END_VAR
RunPermit := Enable AND GuardClosed;
END_FUNCTION_BLOCK
```

可见 Oracle 可以检查部分输入：

| Enable | GuardClosed | 预期 RunPermit |
|---|---|---|
| FALSE | TRUE | FALSE |
| TRUE | TRUE | TRUE |

密封 Oracle 再检查模型没有见过的组合：

| Enable | GuardClosed | 预期 RunPermit |
|---|---|---|
| FALSE | FALSE | FALSE |
| TRUE | FALSE | FALSE |

形式 Oracle 还检查等价性质
`G(RunPermit = (Enable AND GuardClosed))`。有限测试负责捕获具体运行错误，
形式性质用于覆盖测试没有逐一枚举的状态。两者不是把测试步骤当成额外题目。

## 为什么复杂题不能只列一个输入和一个输出

PLC 是扫描周期程序，许多输出取决于历史状态。例如启动/停止锁存的输入序列
可能是：

```text
扫描 1：Start=TRUE  → Running=TRUE
扫描 2：Start=FALSE → Running 仍为 TRUE
扫描 3：Stop=TRUE   → Running=FALSE
```

定时器、计数器、上升沿、故障锁存和多设备协调都必须用这样的多扫描序列
检查。因此每道题仍是一个任务，但一个 Oracle 测试可以包含多个连续输入步骤。

## `reference.st` 为什么存在

`reference.st` 是数据集作者的私有参考实现，不是题面，也不是大模型的输入。
它只用于：

1. 证明题目至少存在一个满足要求的实现；
2. 校准预期输出和形式性质；
3. 在 Oracle 出现矛盾时定位数据集错误。

正式实验只把 `requirement.md` 和 `interface.st` 交给大模型。目录
`packages/internal_v0_1/public_tasks/` 已完成物理隔离，其中没有任何
`reference.st` 或隐藏测试。

## 50 题的组成

数据集覆盖 10 类控制行为，每类 5 题：1 道 easy、2 道 medium、2 道 hard。
总计 10 道 easy、20 道 medium、20 道 hard。

1. 布尔与条件逻辑；
2. 启停与状态保持；
3. 互锁与安全输出；
4. 边沿与事件；
5. 定时器与超时；
6. 计数器与批次；
7. 模拟量处理；
8. 顺序状态机；
9. 报警与故障恢复；
10. 多设备协调。

这 50 道题才是模型需要执行的全部题目。每题最多生成 10 个完整候选，任何
空白、截断、语法错误或擅自改变接口的输出也算一次机会；一旦通过全部可见
验证就提前停止。每题附带的一个 `negative_control` 是自动改坏的参考程序，
仅用于检查 Oracle 是否会抓住错误，不调用大模型，也不计入 50 题。
