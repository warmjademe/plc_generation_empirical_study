# PLC 生成服务交付前鲁棒性测试报告

测试日期：2026-08-23。测试对象为生产 VPS 当前部署版本，真实推理覆盖 DeepSeek V4 Pro 与 Claude Sonnet 5。报告不包含模型密钥、登录凭据、密封测试向量或服务器私有配置。

## 1. 结论

当前版本通过本轮交付前准入。自动化测试、Linux 正反例验证、模型和网络异常处理、需求完整性、强制刷新恢复、幂等提交及并发容量控制均达到预期。DVP48ES300R 和 AS228T-A 的 ST 与布尔梯形图均取得 ISPSoft 3.24 编译和对应 COMMGR Simulator Oracle 的通过证据。

严格测试发现并修复了两个确定性缺陷：OpenPLC 验证脚本与契约生成器的语义审计版本不一致；ISPSoft 原生 LD 导出器不能处理复合表达式上的 `NOT`。两项缺陷均增加了回归测试，并在生产环境重新验证。

## 2. 自动化与静态验证

- 本机完整测试：162 项通过，0 项失败；其中包含 2 项 Node 浏览器恢复测试。
- 生产 VPS：160 项 Python 测试通过，0 项失败。生产机未安装 Node，因此浏览器脚本测试使用本机同版本静态资源执行。
- `python -m compileall -q src scripts` 通过。
- 生产目录仅暴露台达、DVP48ES300R 和 AS228T-A；模型目录仅包含 DeepSeek V4 Pro 与一个 Claude Sonnet 5。Claude 使用 `openai-proxy-anthropic` 的 Anthropic 原生协议；不可用的 Teamorouter Sonnet、DeepSeek V4 Flash 和 Kimi K3 均已移除。
- 不支持的模型和厂商请求均在创建任务前返回 422，不创建后台任务。

## 3. 需求与契约测试

- 12 种完整需求均被接受，覆盖中文紧凑描述、中文分节、英文、表格式和 JSON 风格文本，以及 BOOL、INT、REAL、互锁、锁存复位和顺序控制。
- 13 种不完整或矛盾需求均在调用模型前被拒绝，覆盖接口无变量名、输入输出重名、输出无控制规则、初值不明确、优先级不明确、锁存无退出条件和同条件相反赋值。
- 契约审计会检查需求追踪、状态规则、形式性质、反馈测试、确认测试和优先级反事实；未通过当前审计版本的契约不能自动确认。
- 复杂 AS 顺序控制在前 9 份契约草案存在状态规则问题时均被拒绝，第 10 份通过确定性审计后才进入代码生成，证明倒计时不会绕过契约质量门禁。

## 4. 故障、刷新与并发

- 真实探测中 DeepSeek V4 Pro 和唯一的 Claude Sonnet 5 均在线。不可达的 Teamorouter Sonnet 已从生产目录删除，旧模型 ID 会在创建任务前返回 422；若当前所选通道临时离线，提交门禁返回 503，任务不创建、模型不计费。
- 候选生成阶段的 DNS/连接错误、HTTP 429/5xx、空响应和输出截断均使用有界重试；重试耗尽后终止为基础设施错误，不会被计为程序失败或验证成功。返回网页的错误信息已脱敏，原始诊断仅保存在私有任务目录。
- 浏览器保存任务 ID；若刷新发生在 POST 响应返回前，还保存原请求和幂等键。同一请求重放返回同一 job ID，不会重复启动模型调用。真实任务在轮询暂停 15 秒后仍继续运行并可恢复查看。
- 48 次并发需求检查在 16 个客户端线程下均成功。10 个并发任务创建在容量为 4 时原子接受 4 个、拒绝 6 个并返回 429，没有超额创建。
- 同一模型的并发在线探测使用 single-flight 合并，慢速或离线提供方不会占用全局状态锁。

## 5. 验证器正反例

固定正确程序依次通过 MatIEC、PLCverif、OpenPLC feedback 和 OpenPLC confirmation。固定错误程序被 PLCverif 反例、OpenPLC feedback 和 OpenPLC confirmation 分别拒绝。因此本轮既验证了正确程序可通过，也验证了错误程序不会因验证器失效而形成假阳性。

本轮发现契约生成器输出 `deterministic-contract-semantics-v3`，而 OpenPLC 执行脚本仍固定接受 `v2`。该漂移会把通过 MatIEC 和 PLCverif 的正确候选错误标记为 Oracle 不确定。修复后，OpenPLC 直接导入契约模块中的版本常量，固定夹具同步到当前版本，并增加跨组件版本一致性测试。

## 6. 真实模型与厂商工具链

| 控制器 | 程序类型 | 需求类型 | 结果 | 候选证据 |
|---|---|---|---|---|
| DVP48ES300R | ST | 电机锁存、停止与过载优先 | 通过 | 1 个候选；MatIEC、PLCverif、两组 OpenPLC、ISPSoft 与 DVP-ES3 Oracle 全部通过 |
| DVP48ES300R | LD | 双电机互锁 | 通过 | 1 个候选；原生 `[FB,LD]` 经 ISPSoft 与 DVP-ES3 Oracle 通过 |
| AS228T-A | ST | 两阶段顺序控制 | 通过 | 1 个候选；Linux 全链及 ISPSoft/AS200 Oracle 通过 |
| AS228T-A | LD | 自动/手动阀门安全控制 | 通过 | 同一候选先通过 Linux 全链；导出器修复后通过 ISPSoft/AS200 Oracle，覆盖 R1--R4 |

DVP ST 端到端任务使用 1 个候选，耗时约 313 秒。其提交使用同一幂等键模拟响应丢失，两次提交均返回同一任务。其余三项并发提交后的矩阵耗时约 707 秒，Windows worker 按设计串行执行厂商仿真。

AS 梯形图首次运行的第 4 个候选已经通过 MatIEC、4/4 PLCverif 性质和两组各 4/4 的 OpenPLC 观察，但原生 LD 导出器拒绝 `NOT(A AND B)`。修复后，导出器用德摩根律把复合取反转换为并联常闭触点；同一候选、同一 Ladder IR 随后通过 ISPSoft 3.24 编译和 COMMGR AS200 全案例 Oracle。该修复扩大的是确定性导出器的已校准布尔子集，没有放宽任何验证门禁。

Claude Sonnet 5 使用 Anthropic 原生协议完成了相同的四项矩阵，结果为 4/4：DVP48ES300R 的 ST 与 LD、AS228T-A 的 ST 均在第 1 个代码候选通过，AS228T-A 的 LD 在第 2 个候选通过；四项的厂商验证状态均为 `passed`。完整矩阵耗时约 863 秒。AS LD 的第 1 个候选被 PLCverif 拒绝，第 2 个候选根据形式反例修正后通过 9/9 性质、两组各 11/11 OpenPLC 观察和 AS200 Oracle，表明 Sonnet 通道能够使用验证反馈完成迭代。

## 7. 当前边界

- 原生 LD 仅支持已校准的布尔触点和普通、置位、复位线圈；比较、算术、定时器、计数器和边沿块仍失败关闭。
- 厂商仿真依赖交互式 Windows 会话，复杂多阶段 Oracle 的耗时可达数分钟；页面会持续显示模型、Linux 验证和厂商 worker 的阶段日志。
- 浏览器恢复信息位于当前标签页的 `sessionStorage`；退出登录会主动清除。服务进程被强制重启时，进程内活动任务会失败关闭，而不会错误恢复为成功。
- 本报告证明程序满足冻结契约和已执行 Oracle，不等同于对现场接线、机械风险和安全认证的替代。客户投产前仍需按设备风险等级进行真实 PLC、I/O 和急停回路验收。
